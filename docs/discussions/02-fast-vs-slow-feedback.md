# Discussion 02 · 反馈周期决定一切

Date: 2026-05-01

## 一句话

**任何产品的"健康度"先看反馈周期**——这个数字决定它需不需要重型反向调节。

## 三档反馈周期

| 反馈周期 | 飞轮形态 | 反向调节 | 例子 |
|---|---|---|---|
| < 1 day | 自健康 | 不需要 | tg-calendar / 短视频推荐 / 拼写纠错 / IDE 补全 |
| 1 day – 1 week | 可健康 + 轻量调节 | 需要漂移监控 | 新闻推荐 / habit tracker / 健身 app |
| > 1 week | 容易毒化 | **必须**重型反向调节 | 求职 / 投资 / 教育 / 长期健康 |

## 为什么短反馈循环自健康

机制：
1. 你今天做了一个分类决定（比如 tg-calendar 把"和 AI 写论文"分错为黄色）
2. 明天打开看到颜色不对——你立刻改
3. 学习更新 → 后天默认对了
4. 一周内系统稳定校准

错误**没有累积空间**——它在被察觉的同时就被纠正。这是任何"今天做、明天看效果"的产品的护城河。

## 为什么长反馈循环容易毒化

求职反馈循环：
1. 你今天 thumbs-up 一个岗位
2. 投了 → 等回复（几天到几周）
3. 面试 → 几周后
4. offer 或拒（几周到几个月）

完整反馈要数周。一年才能积累 ~50-100 次完整反馈。

这意味着：
- 算法学到的是**几周前**的偏好
- 你这周的"漂移"要几个月后才显形
- 错误大量累积——而且彼此遮蔽

求职软件设计里**没有反向调节就一定会毒化**。

## tg-calendar vs Compass — 一个对照实验

把两者放一起看：

| 维度 | tg-calendar | Compass |
|---|---|---|
| 反馈周期 | 几小时 - 1 天 | 几周 - 几个月 |
| 错误纠正速度 | 立刻 | 几个月后才显形 |
| 学习是否健康 | ✓ | 默认会跑偏 |
| 反向调节投入 | 0 | 4 件套（drift / adversarial / assumption override / 价值观回归） |

设计 Compass 的反向调节时**不需要**给 tg-calendar 也加——这是过度设计。
反过来，tg-calendar 的"自然健康"经验**不能**直接搬到 Compass——这是错误简化。

## 设计任何新产品时第一个问题

不是"用什么 LLM"、不是"什么数据库"、不是"前端用什么"。

是：**反馈周期是几天？**

这一个数字决定：
- 需不需要做反向调节
- 学习速率应该多快
- 错误兜底机制要多重
- metric 的有效观察窗

## 这条 discussion 落地到的 ADR

- tg-calendar ADR-0005 (Fast feedback flywheel — 显式说明为什么不加反向调节)
- Compass ADR-0004 (Reflective Flywheel + 反向调节)
- Compass calibration_learner.py 的 slow drift 设计（每次 ±1）
- Compass 价值观回归 checkpoint 频率（默认 14 天）

## 给后来人

如果你做新产品，把这条贴在墙上：

> **短反馈循环 = 数据小但迭代快 = 飞轮自我修正**
> **长反馈循环 = 数据大但迭代慢 = 飞轮一旦跑偏很难拉回**

不要假装它们是同一种问题。
