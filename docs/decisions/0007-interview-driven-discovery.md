# ADR-0007 · 访谈式发现而非 LLM 单方面改写

Status: Accepted
Date:   2026-05-01

## 情境

简历改写时常见痛点：用户说"工科生很少写课程小项目，事实层稀薄"。
表面看是事实**不足**——是不是要让 LLM 帮"创造"一些事实？

但深究：90% 的"事实不足"其实是**挖掘不足**——用户做过一堆课程项目、实验、
课设，但他不认为这些值得写。LLM 不需要编造，需要**问问题让用户回忆**。

## 选项

### A. LLM 单方面看简历改写（标准做法）
- ✓ 简单
- ✗ LLM 没看到用户没写下来的细节——只能在已写部分玩花活
- ✗ 容易跨过 L4-L5 边界（"build pipeline" → "build pipeline processing 10M records"）

### B. 让用户手动补充更多细节（"请详细描述这个项目"）
- ✓ 不编造
- ✗ 用户不知道补什么——他根本不觉得课程项目有价值

### C. LLM 主动提问 + 用户回答 + 合成新原子事实
- ✓ 把"挖掘"工程化——LLM 知道问什么（数据规模 / 算法 / baseline / 团队角色等）
- ✓ 用户回答的内容**全部是真事实**——零编造
- ✓ 新事实进入事实层（不可变），后续改写有了更厚的素材
- ✗ 多一步交互（用户要花时间回答）
- ✗ 多次 LLM 调用（生成问题 + 合成事实）

### D. 接 ESCO / O*NET 数据补充行业标准技能
- ✓ 客观
- ✗ 标准化数据 ≠ 用户具体经历
- ✗ 不解决"用户不知道自己经历值钱"的核心问题

## 决定

**选 C** —— 访谈引擎。

工作流：
```
fact "Built electrical grid simulation in coursework"
  ↓
LLM 生成 5-8 个具体问题（针对该 fact 的 kind/text）
  ↓
用户回答（可空）
  ↓
LLM 合成新原子事实（user_verified=True）+ FactEvidence 链回访谈
  ↓
新 facts 作为 source 喂给改写流水线
```

关键约束：
- 问题必须**具体到该 fact**，不能问通用问题
- 合成事实必须**严格依据用户回答**——禁止推测
- 新事实自动 `user_verified=True`，享受高 amplification level

## 代价 / 后果

- 用户要花时间回答问题（一次 5-10 分钟）—— 但是一次性投入
- 多次 LLM 调用（生成 + 合成）——成本上升
- 用户偶尔跳过所有问题——这种情况不合成新 fact，原 fact 仍可用
- 问题质量取决于 LLM——偶尔会问无意义的问题

什么时候会后悔：
- 如果用户从来不用访谈功能 → 简化交互（如：访谈集成到上传流程，强制走一遍）
- 如果合成的 fact 质量不高 → 加用户审核步骤（合成完让用户 approve 再入库）
